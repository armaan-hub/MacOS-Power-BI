## Why
- The repo has 0 git tags after 282 iterations, so there is no marker for "this version worked".
- The full gate replays all 540,401 saved Power BI answers on every change (about 18 minutes with xdist). That is how we stay safe today, but it grows with every chapter.

## What "closing a chapter" means
A chapter is closed when all five are true:
1. **Done list** written in `CHAPTERS.md`: what works, what is refused on purpose, and what is out of scope.
2. **Full gate passes** (`PYTHONPATH=. python tools/parity_check.py --tests` says PARITY GATE PASSED) and the lock count is recorded.
3. **Team-Thinker verdict PASS** on the done list (it checks the list against the gate output and the saved answers).
4. **Git tag** `chapter-N-<name>` on the merge commit, pushed.
5. **Close report** (one page, `docs/chapters/chapter-N.md`): numbers, REA evidence used, known gaps.

After closing:
- No new features in that chapter. New work goes to the open chapter.
- A closed chapter's saved answers keep running automatically. If one breaks, it is a regression and is fixed at once (it is not reopened as feature work).
- Saved Power BI answers are never edited.

## Changes after Team-Thinker's review (PASS WITH CHANGES, 2026-11-17)
- **Pending is not "refused on purpose".** In `tools/parity_check.py` (`status()`), `gap-reject` means Power BI gave an answer and our app refused, so it is unfinished work. A gate PASS only fails on DIFF, CRASH or a lost lock. So every done list must split the pending items into: later work (moved to a named future chapter), known deviations (`known_deviations.json`), and out of scope. Chapter 1 is renamed **"DAX engine baseline"**: everything that matches is locked; the pending DAX items move to **Chapter 1b "DAX gaps"**, which is not closed.
- **Numbers come from a fresh gate run**, never from memory or an old `PARITY_LEDGER.md`. Any matched-but-unlocked items are locked with `--accept` or listed.
- **A tag alone cannot replay the gate.** The VAT workbook (`tests/Data/`) is gitignored and `~/Downloads/DSI.xlsx` is missing, so DSI table answers are skipped. Each close report records which table answers were actually replayed and the SHA-256 of each workbook used.
- **Saved answers cannot be split inside DAX.** They are 137 `dax_battery*.json` + 60 `taskNN_*_spec.json` files named by iteration, locked as `file:expr` in `baseline.json`. So Chapter 1 = the whole DAX list. The sample gate maps chapters to whole battery files only.
- **UI chapters (3, 5) have no saved answers.** They close by a checklist: each screen item checked against Power BI on the VM screen, with a screenshot reference, plus the gate passing.
- **Sample gate must be read-only**: a sampled run never writes `PARITY_LEDGER.md` or `baseline.json`, and `--accept` refuses to run with `--sample`.
- **Tags**: annotated, only on a clean merge commit, pushed by name (`git push origin chapter-1-dax-baseline`), never moved or deleted.

## Only one chapter open at a time
The team has one coding agent at a time, so one open chapter keeps the focus. A small fix in another area is allowed only if it is a regression.

## Two gate sizes (later, needs code)
- **Task gate** (every task): full replay of the open chapter's answers + pytest for the touched area + a fixed sample of each closed chapter's answers.
- **Chapter gate** (when a chapter closes, and before every push to GitHub): everything, as today.
- Until the sample option exists in `tools/parity_check.py`, every task keeps running the full gate.
- Risk: a sample can miss a regression until the next full gate. Mitigation: the full gate runs before every push.
