# Task 171 — dax-hunt-171: CONVERT(number, DATETIME) keeps Power BI's 1/300-second ticks or is refused (batch 28)

Goal: 2024 fresh random expressions over 14 function groups (t220) left 10 wrong; 9 are known last-digit limits. The
other: CONVERT(CONVERT(CONVERT(1E-5,DOUBLE),DATETIME),DOUBLE) is 9.99228395061728E-06 in Power BI (a DATETIME keeps time
of day only to 1/300 s, 25,920,000 ticks a day) and the app kept the raw 0.00001.

Spec: t220 (2024 random rows); t221 dtall (140 rows over five rounds) and t222 (40 rows set by the Sonnet head), all
measured in Power BI. None is read by the app. The measurements show Power BI's rounding depends on its query plan, not
on the value: constants are rounded; values touching SUM, SUMX, AVERAGE(X), MEDIAN, COUNT(A/X) or PRODUCTX (even
SUM(..)*0+1E-5 or an IF condition on SUM), COUNTROWS(FILTER(..)) and MAXX(Facts, expr) are not; COUNTROWS, MIN/MAX,
DISTINCTCOUNT and SELECTEDVALUE are. That cannot be modelled reliably, so the app answers only when it is sure.

Work (Haiku 5.5 coded; Sonnet 5.5 headed review and testing with read-only Haiku testers):
- analytics_studio/dax_dates.py: `number_as_datetime` rounds a serial to the nearest tick (day and time of day handled
  separately and recombined in double arithmetic, so -1E-5 gives -9.99228395059948E-06 as in Power BI) and clamps the
  last day 9999-12-31 to its last tick; `is_on_tick` tells whether rounding would change a value.
- analytics_studio/measures.py: CONVERT(x, DATETIME) returns an on-tick value unchanged, rounds an off-tick value whose
  argument is constant (`_constant_node`: literals, operators, pure calls, VARs bound to constants), and refuses an
  off-tick value whose argument reads the model. Date arithmetic (DATE/TIME +/- number) is unchanged.
- analytics_studio/dax_typed.py: VALUE of a date/time goes through its text, as in Power BI (whole seconds); where the text
  cannot be read back it is refused.
- tests/test_iteration259_hunt_171.py: 11 tests.

Review: the first version rounded every CONVERT and turned 6 rows that main had exact into wrong ones (SUM-based values,
which Power BI does not round); the second also refused non-constant date arithmetic, which contradicts saved Power BI
answers (date + column / 3 inside iterators is rounded), so the refusal was limited to CONVERT.

Accepted coverage loss (refusals, never wrong): about 43 probe rows exact on main are now refused (non-constant off-tick
CONVERT that Power BI happens not to round), plus VALUE(DATE(100,1,1)) and VALUE of an exact half second.
Left as known limits: DATE(2020,1,1)+SUM(..)/1E6 style date arithmetic (Power BI does not round it, the app does, same as
main); the last-digit limits of NOMINAL, LN, SIN, EXP-based statistics, CONFIDENCE.T and the BETA.INV solver.
Later items (not blocking): UTCNOW/UTCTODAY as volatile in the constancy walk; the same refusal for text sources of
CONVERT; narrow VALUE refusals to real text round-trip failures; restore the shapes Power BI rounds (MAX, MIN, COUNTROWS,
DISTINCTCOUNT, SELECTEDVALUE) once measured.
