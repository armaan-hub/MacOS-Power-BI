## Part B review outcome (Claude, 2026-10-28)
Built by Antigravity (all 61 saved items matched, computed from the semantics, no lookup), then 8,478 fresh shapes asked of live Power BI found 553 differing answers (before the fixes). Five wrong rules, all fixed:
1. **Levels in groupBy order.** The first build gave every showAll column its whole domain. Power BI builds the rows level by level in groupBy order: a showAll level takes the values of its column that exist in the model beside the values chosen for the earlier levels; any other level takes only the values the table already holds there; where a level has nothing, the columns from there on are BLANK; with an empty table and a non-showAll first level nothing is added. Added rows follow the model rows grouped by the groupBy columns they hold (the order SUMMARIZE lists them), placeholders by the leading real columns.
2. **Types.** Loaded cells are text; the table's rows are typed before they are compared with the model's values (numeric columns never matched).
3. **Errors.** A showAll column named twice among the groupBy columns is an error (a repeated plain groupBy column is not). The join uses data lineage, so SELECTCOLUMNS/DATATABLE/ROW tables give "No common join columns". A column after a filter table is an error. DISTINCT read directly over ADDMISSINGITEMS is an error (FILTER, ADDCOLUMNS, TOPN, UNION, SELECTCOLUMNS around it work).
4. **TOCSV order.** The printed order is the table's own order with the added rows after it, so only a table whose order is modelled is accepted. The 9 saved TOCSV items over SUMMARIZECOLUMNS matched only by luck (West and North swap in a fresh probe) and are now refused (as TOCSV of SUMMARIZECOLUMNS is). Also fixed in older code found on the way: TOCSV of a several-column ALL and of CALCULATETABLE(SUMMARIZE over a numeric column, filter) printed a wrong order, now refused.
5. **One table.** Columns of more than one table are refused (not probed). `ADDMISSINGITEMS(table)` with a single table is the table.
Review batteries: `dax_battery_ami_extra` (4,724), `dax_battery_ami_extra2` (3,743); tests `tests/test_iteration96_table_fns_2_b_review.py`. Eleven shapes that hit older gaps were left out of the batteries (see HANDOFF open questions). **Lesson for Part C:** a result that "matches the saved items" may be luck in row order; check order with a case where the groups are not already in alphabetical order, and probe the rule on fresh shapes before trusting it.
