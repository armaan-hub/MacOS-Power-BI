## 1. Why the plan changes

1. The DAX hunt (Tasks 184 to 246) has no finish line. Fresh shapes are still 6 to 13% wrong after 60 tasks.
2. The engine is slow on real data: 6.7 s for a simple SUMX on 100,000 rows; 20 s on 2,000 rows for `SUMX(Facts, CALCULATE(...))`.
3. All saved answers come from a 6-row table. Time intelligence has 0 replayed answers.
4. Fixes are shape patches. `measures.py` is 26,531 lines.
5. Probe data (5.1 GB) is outside git.

## 2. What stays the same

- The parity rule. Power BI is the authority. Saved Power BI answers are never edited.
- "Unsure means refuse." No answer lookups.
- One coder at a time. One branch per task in the one project folder. Delete nothing.
- Opus plans, verifies and merges; it writes no code. Sonnet heads review and testing. Haiku testers are read-only.
- The gate must say PARITY GATE PASSED before any merge.
- VM rules: one Power BI probe run at a time, never save the Power BI project, headless only.
- Say "Power BI answer check", never "oracle".

## 3. The new order of work

Phases run one after another. Each phase has an exit test. Opus does not start a phase until the exit test of the one before it passes.

### Phase 0: Close the hunt safely (about 1 day)
- **0.1** Let Task 246 finish through the normal loop. It is the last hunt task.
- **0.2** Freeze the hunt data. Coder task: turn the measured rows in `pbi_scratch/w221` to `w246` and `review221` to `review246` into new battery files `tools/parity/dax_battery_hunt_NNN.json` (expression, table rows used, Power BI answer). Rows on the second, third and fourth Facts tables need the table stored with the row; extend the replay to accept a table per item. Do not re-measure; these answers are already Power BI answers.
- **0.3** Run the gate, then lock (`--accept`). This also locks the 554 matching rows that are not locked today.
- **0.4** Copy `pbi_scratch` briefs and probe folders to a second disk or a private git repo.
- **Exit test:** gate passes; saved-answer count is above 540,401; `locked` equals `match`; a copy of `pbi_scratch` exists.

### Phase 1: The DAX exit test (about 1 week)
This replaces "hunt until nothing is wrong" with a fixed list.
- **1.1 Model.** Build one realistic model in the guest and the same model locally: a Date table (3 years), a Sales fact table (at least 10,000 rows), and Product, Customer and Region tables with relationships (one inactive relationship, one many-to-many bridge). Keep the build script in `tools/`. Never save the guest project; rebuild from the script.
- **1.2 Formula list.** Sonnet writes about 400 formulas that people really use. Sources: Microsoft's DAX documentation examples, the DAX patterns that are public (time intelligence, year-to-date, previous year, moving average, percent of total, ranking, top N, running total, ABC classes, new versus returning customers, budget versus actual, semi-additive balances). Each formula is evaluated under several filter contexts (by year, by month, by product, by region, grand total). Armaan may add formulas from his own reports.
- **1.3 Measure.** One chained Power BI run. Save as `tools/parity/dax_battery_exit_*.json`.
- **1.4 Score.** Report right, wrong, refused, crash, and the time per formula.
- **1.5 Fix loop.** Work the wrong rows first, then the refused rows, in groups by cause. Normal loop: Haiku codes, Sonnet reviews, gate.
- **Exit test (this is the finish line for DAX):** 0 wrong, 0 crash, at least 97% answered (the exact share is Armaan's decision), all locked. After this, DAX work is only bug reports against real formulas.

### Phase 2: Speed (about 1 to 2 weeks, overlaps the end of Phase 1 in planning only)
- **2.1 Benchmark.** New tool `tools/perf_check.py`: the exit-test model at 10,000, 100,000 and 1,000,000 rows; about 30 formulas; prints seconds per formula. Read-only, under 5 minutes.
- **2.2 Targets (proposal).** At 100,000 rows: simple aggregates under 0.1 s, row iterators under 1 s, context transition inside an iterator under 2 s. No formula may grow with the square of the row count.
- **2.3 Work items, in this order:**
  1. Find why `SUMX(Facts, CALCULATE(SUM(...)))` is quadratic (profile with `cProfile` first; do not guess). Expected cause (guess): each row re-filters the whole table. Fix with an index per column or by grouping equal rows.
  2. Row iterators: compile the row expression once instead of walking the tree for every row.
  3. Store columns as arrays instead of one dict per row where the profile says it matters.
- **2.4** Add the benchmark to the gate with a limit (fail when a formula is more than 2 times slower than its saved time).
- **Rule:** every speed change must keep all saved answers. The gate is the safety net; that is what the 540,000 answers are for.
- **Exit test:** targets met at 100,000 rows; gate passes.

### Phase 3: Engine structure (runs inside Phases 1 and 2, never as a big rewrite)
- **Rule P1, no shape patches.** A fix must state a rule about DAX meaning in one sentence ("an added column of SUMMARIZE sees its group as whole rows"). A function that matches one tree shape and rewrites or refuses it is not accepted. Sonnet's review rejects it.
- **Rule P2, one refusal place.** When no rule is known, refuse in one central table of "not modelled" cases, not in scattered matchers.
- **Rule P3, size cap.** `measures.py` must not grow. New code goes into a `dax_*.py` module. Each task that touches a function family moves that family out of `evaluate()` into its own module, behind the gate.
- **Rule P4, no task numbers in code.** Docstrings state the rule; history is in git.
- **Exit test:** none; these are standing rules. Opus tracks the line count of `measures.py` per task in the handoff board.

### Phase 4: Power Query M (the user's stated next track)
- **4.1 Count first.** Of the 430 Power BI names missing locally, list which are standard-library functions and which are connectors. Connectors are out of scope unless Armaan names one.
- **4.2 Measure what exists.** The 651 local names have no replayed Power BI answers in the gate. Build M batteries the same way as DAX (`tools/m_oracle_diff.py` exists). Remember the known trap: `int.MinValue` and long evaluations hang Power BI.
- **4.3 Exit list first.** As in Phase 1: write the list of M steps the Power Query screens generate (Group By, Split, Merge, Pivot, type changes) and the 100 most used functions; that is the exit test.
- **4.4** Resume Chapter 3 (Group By and Split dialogs) with it.

### Phase 5: Report view
