# Task 70: RANKX audit (rankx-audit-60)

**Goal:** RANKX values and the row order of iterators whose body is a RANKX match Power BI Desktop. Where no rule reproduces the evidence, the engine refuses instead.

**Evidence:** `tools/parity/task70_rankx_audit_spec.json` holds 266 rows that main gets wrong, from a 1,500-expression audit grid probed on Power BI (scratchpad `t70a/pb.json`).

**Parts:**
- **A, RANKX values (31 rows).** These are mostly DENSE ranks. Power BI ties BLANK with 0 when it counts dense ranks, but we count them as separate values. Example: `RANKX(ALL(Facts),CALCULATE(SUM(Facts[Sales])),,DESC,DENSE)` gives `2,1,5,4,4,3` in Power BI and `2,1,6,4,4,3` from us. Some rows in this part also have the order issue from part B.
- **B, walk order (234 rows).** The values are the same as Power BI's but the order differs. `CONCATENATEX(Facts, RANKX(...))`, unfiltered and under CALCULATE filters, walks the outer Facts in a different order from Power BI. The walk seems to depend on the columns the RANKX body reads. Example: `CALCULATE(CONCATENATEX(Facts,RANKX(ALL(Facts),Facts[Note]),","),Facts[Sales]>0)` gives `5,5,1` in Power BI and `1,5,5` from us.
- **C, CONCATENATEX order-by (1 row).** CONCATENATEX with two equal ORDER BY keys (`Facts[Note],DESC,Facts[Note],DESC`) under a filter.

**Rules:**
- Compute the answer. Never key on names or expressions. App code never reads `tools/parity`, fixtures or the scratchpad.
- No row that matches on main may change status.
