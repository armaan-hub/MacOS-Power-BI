## The problem
When TOPN's sort values tie, Power BI keeps every tied row at the cut-off, and the order in which the rows of the TOPN result are then walked (by CONCATENATEX, etc.) depends on N and on the ties. The engine walks them in another order. Facts rows in storage order (Sales/Quantity/Region): `10.5/2/East | 20/3/West | -1.5/1/East | (blank)/4/North | 0/0/West | 2.5/5/East`.

Examples (Power BI vs engine):
- `CONCATENATEX(TOPN(1,Facts,INT(Facts[Sales]/100)),Facts[Sales],"|")`: Power BI `0|2.5|10.5|20`, engine `10.5|20|0|2.5`.
- the same with TOPN(2): Power BI `2.5|0|10.5|20`; with TOPN(3): `10.5|2.5|0|20`.
- `CONCATENATEX(TOPN(1,Facts,Facts[Sales]>50),Facts[Sales],"|")` (every row ties): Power BI `|-1.5|0|2.5|10.5|20` for N = 1..4.
- `CONCATENATEX(TOPN(4,Facts,Facts[Region]),Facts[Sales],"|")`: Power BI `10.5||-1.5|20|0|2.5`.

Read all 42 wrong rows with the scorer. A different order for different N suggests a heap-based or partial selection over the rows in storage order, with the output in the selection structure's internal order. Find the algorithm that reproduces **every** spec row.
