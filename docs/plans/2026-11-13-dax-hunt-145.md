# Task 145 — dax-hunt-145: wrong DAX answers from a fresh 14-group hunt (batch 3)

Goal: remove the wrong answers found by 840 fresh random probes (14 groups x 60, seeds 4501+), 86 backlog probes and
residual-amplifier diagnostics, checked against Power BI Desktop in the guest. Refusing is always better than guessing.

Spec: 961 measured expressions (`spec`) plus a hidden `holdout` (36). None is read by the app.

Families (Haiku 5.5 coded, Sonnet 5.5 reviewed and tested in the real app):
- A. MROUND with a fractional multiple (quotient below 1E15), and FLOOR/CEILING/MROUND with a negative number and a
  negative fractional significance, round in binary double: MROUND(7,1E-5)-7 = 8.88178419700125E-16,
  FLOOR(-7,-1E-5)+7 = -8.88178419700125E-16, ODD(MROUND(7,1E-5)) = 9. Integer multiples keep the exact Decimal path.
- B. DIVIDE with a text number returns the double quotient: DIVIDE("12",123456789.123) = 9.72000007876797E-08.
- C. CONVERT(number, DATETIME) keeps the full value for numbers before year 100 (round trips to -1E15 are exact); the
  display is 01/01/0100, as Power BI shows.
- E. FV, PV, PMT, NPER and RATE return the exact double: FV(0.05,1,6)+6 = -5.32907051820075E-15.
- D. Not changed: INFO.* answers depend on the guest model's current tables (a scratch table was present), so they are
  not a test of the app.

## Results
Scorer: spec 898 -> 914 exact, 31 refused, 32 -> 16 wrong; holdout 34 exact, 2 refused, 0 wrong; Task 143 and Task 144
sets unchanged. Real app: 16 probes created as measures, all equal to Power BI.

Known limits moved to the hunt backlog (last-digit precision, not refused): COS/SIN/SINH/TAN/BETA.INV differ from the
correctly rounded result by about 1 ulp in Power BI; XIRR's early stop differs after about 13 digits; a financial result
combined with a literal and amplified by 1E15 is added in Decimal, not double.
