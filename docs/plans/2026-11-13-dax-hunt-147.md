# Task 147 — dax-hunt-147: wrong DAX answers from a fresh 13-group hunt (batch 5)

Goal: remove the wrong answers found by 780 fresh random probes (13 groups), 86 targeted CEILING/FLOOR probes and
40 targeted table-in-scalar probes, checked against Power BI Desktop in the guest. Refusing is always better than
guessing.

Spec: 935 measured expressions (`spec`) plus a hidden `holdout` (12). None is read by the app.

Families (Haiku 5.5 coded, Sonnet 5.5 reviewed and tested in the real app):
- A. CEILING / FLOOR / ISO.CEILING with a whole-number significance: Power BI computes the quotient as a double,
  rounds it to 15 significant digits, then takes ceiling/floor and multiplies back. CEILING(-1E15,-3) =
  -999999999999999, FLOOR(300000000000002,3) = 300000000000003, while CEILING(-1E14,-3) = -100000000000002 keeps its
  fraction. The app was wrong between about 1E14 and 1E15; it now follows the rule for every |number| < 2^53.
  An exact 15-digit tie on a negative quotient rounds toward +infinity, fitted to the locked row
  CEILING(-617673396283947,2).
- B. A table expression in a scalar position is a compile-time error in Power BI, even in a branch that never runs
  (IF(TRUE(),1,x), IFERROR(1,x), SWITCH): tables with more than one column ({(1,2)}, ROW with two columns, a bare
  table name) and DATESMTD/DATESQTD/DATESYTD/PREVIOUS*/NEXT*/FIRSTDATE/LASTDATE/STARTOF*/ENDOF* whose first argument
  is not a column. The app now refuses these at parse time. One-column tables stay legal.

Not done: IF(TRUE(),1,ALL(Facts[Region])) is 1 in Power BI but the app refuses it (measure-level table gate); it was
refused before this task too, so it moves to the hunt backlog.
