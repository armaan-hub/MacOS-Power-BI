## Part A: VAR inside operators, iterators and CALCULATE filters (20 items, battery `dax_battery_var_scoping`)
Shapes: a `VAR ... RETURN` as the right side of a comparison or `&` (`1>VAR y=2 RETURN y`, `"a"&VAR y="b" RETURN y`); a table VAR read by DISTINCT, SUMX, FILTER, or by another VAR (`VAR t=Facts RETURN SUMX(t,Facts[Quantity])`); a VAR inside a CALCULATE filter argument (`CALCULATE(COUNTROWS(Facts),VAR t = 2 RETURN Facts[Quantity]>t)`, nested VARs, a VAR holding a column `Facts[Quantity]` used as `t>2`, `t IN {1,2}`, `ISBLANK(t)`), and the same inside CALCULATETABLE.
The scoping rules are the ones of Task 2 (`docs/plans/2026-10-26-var-scoping-1.md`, already locked). A VAR that holds a column reference in a filter keeps the column's lineage: `VAR t = Facts[Quantity] RETURN t>t` is BLANK, `RETURN t` alone is 5 (look at the saved answers to see what Power BI does, then find the rule; do not special-case the text).

## Review outcome (Claude, 2026-10-29)
Tested against Power BI Desktop 2.157.879.0 on the iPad guest (opened with the user's OK, queried headless, project never saved) and in the real app (offscreen). The build computes (no lookup) and matched the saved items, but two rounds of fresh shapes (3,033 + 3,005, each also on two Facts tables whose rows come in another order) found:
1. **Wrong values (fixed):** a text or True/False value beside a VAR block (`"a"<>VAR y=BLANK() RETURN y`, `""=(VAR y=BLANK() RETURN y)`, `"x"=VAR y=BLANK() RETURN LEN(y)`) is an error in Power BI (the block has the static type of its RETURN expression: Integer); the first build answered True/False. Fixed in the comparison branch with the static type of the block; a block whose type is not known beside a text or True/False value is refused.
2. **Too broad (fixed):** the rule "a BLANK variable is a number" was applied to every iterator, so 23 fresh shapes that main answered (`COUNTROWS(FILTER(Facts,VAR t=BLANK() RETURN Facts[Region]=t))`, a text column beside a variable holding a BLANK column value) were refused. It is now scoped to the CALCULATE filter route where the saved answers show it.
3. **Order (fixed by refusing):** `VAR t=TOPN(...) RETURN CONCATENATEX(t,...)` listed the rows in another order than Power BI (the walk order of a TOPN depends on the rows its consumer reads, which a variable hides); refused.
4. Five older wrong answers of main (`COUNTROWS(CALCULATETABLE(Facts,VAR t=SUM(...) RETURN ...))`) are now correct (refused) because variables in CALCULATE filters hold only a column or a constant.
Refused on purpose (valid in Power BI): a VAR block on the right of `||`, `&&`, `^`; a CALCULATE filter variable holding an expression (`1+1`, `SUM(...)`, a measure); `SUMX(t,1)`/`FILTER(t,TRUE())` over a bare table variable; the sdet/round2 to round5 leftovers (24 items, listed in `PARITY_LEDGER.md`).
Open (older than Task 9, logged in `HANDOFF.md`): the walk order of `DISTINCT(Facts)` when every row is distinct (differs on one of three Facts tables); TOPN with tied sort values; a text column compared with COUNTROWS of an empty CALCULATETABLE/FILTER (BLANK here, an error in Power BI because COUNTROWS is typed Integer).
