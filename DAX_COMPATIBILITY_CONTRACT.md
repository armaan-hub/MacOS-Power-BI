# DAX compatibility contract

**Status:** Audit baseline; no claim of Power BI DAX parity.

This document describes the DAX behavior currently implemented by Analytics Studio's local Python evaluator. It is a product compatibility contract, not a reference to the complete DAX language. Microsoft’s [DAX function reference](https://learn.microsoft.com/en-us/dax/dax-function-reference) covers more than 250 functions and notes that support varies by product and version.

## Target runtime

- **Product/runtime:** Analytics Studio's local, native desktop analytics application and its saved `.npa` project model.
- **Platform:** macOS is a target platform. Microsoft Power BI Desktop's [minimum requirements](https://learn.microsoft.com/en-us/power-bi/fundamentals/desktop-get-the-desktop) specify Windows 10 or Windows Server 2016 or later; this application is not Microsoft Power BI Desktop.
- **Storage/model engine:** Local imported tables, local relationship metadata, and a bounded safe Python evaluator. The evaluator parses expressions into a small AST; it does not call a Tabular/VertiPaq engine, execute Python supplied by a user, or load PBIX/TMDL models.
- **Version target:** No specific Microsoft engine/version is currently claimed. A versioned target requires the engine feasibility decision recorded below.

## Calculation object scope

| Object | Current behavior | Current boundary |
|---|---|---|
| Measure | Persisted name and expression; optional description, display folder, and hidden flag; evaluated for the local report context and displayed in supported report workflows. | Numeric/scalar subset; format strings, home-table reassignment, general DAX result types, and complete visual query context are not modeled. |
| Calculated column | Persisted name and expression; recalculated row by row after source refresh. | Bounded numeric/boolean expressions over the owning table; general cross-table `RELATED` behavior and broad DAX context are unavailable. |
| Calculated table | Saved query dependency and refresh behavior. | Only a one-column `DISTINCT('Table'[Column])` definition is supported; this is not a general DAX table-expression engine. |
| Power Query custom column | Separately authored in the local M-style expression subset and replayed at source refresh. | Not a DAX calculated column and not a full Power Query M function runtime. |
| Visual calculation | Unavailable. | Not parsed, persisted, or evaluated. |

## Current semantic boundaries

- Expressions are parsed into a small AST with length/token limits. Arbitrary Python or other host-language execution is not allowed.
- Scalar values are predominantly normalized text or decimal numbers. This is not the complete DAX Variant type system; blank, coercion, collation, error, and locale semantics can differ.
- Measures use the current report/page/visual filter and relationship paths, but the evaluator does not model all visual row/column query-axis context. A bounded exception supports an explicit qualified `ALLSELECTED('Table'[Column])` modifier when a saved measure is evaluated in a non-stacked chart with one categorical axis bound to the measure's same model table: it removes the current chart category and restores the filtered visual category set captured before local Top N trimming, while retaining other column and relationship filters. This path is tested with a page selection on the axis, a separate Month filter, a related-table Month filter root, a plain-aggregate chart control, a Card control, a pre-Top-N selection control, and save/reopen/changed-source refresh. It does not extend to no-argument or table `ALLSELECTED`, legends, stacked charts, multiple axes, matrix/table visual totals, cross-table grouping, or every nested visual query shape; the editor's standalone preview still has no visual-axis context.
- Row context exists in bounded `SUMX`, `AVERAGEX`, `MAXX`, `MINX`, `COUNTX`, and `COUNTAX` paths. `MAXX` and `MINX` accept a loaded table or supported `ALL`, `ALLNOBLANKROW`, or `ALLSELECTED` table/column argument (and `FILTER`, iteration 67) and a numeric, date or blank row expression. Their two-argument measure forms ignore blank results and return local BLANK when no numeric result remains; this empty/all-blank behavior is an inference, not verified against a Tabular engine. They accept date results (the answer is the date itself) and reject the optional variant argument, Boolean-only results, arbitrary table expressions, and calculated-column use. Since iteration 87 a row expression whose IF / SWITCH / IFERROR / COALESCE branches differ in type (a Variant) is read like Power BI reads it: `COUNTX`, `SUMX`, `AVERAGEX`, `MAXX` and `MINX` take only its numbers and dates, `COUNTAX` every non-blank row; a few nestings (a number-and-date branch inside a Variant, a mixed `COALESCE` whose later argument can fail, a True/False under a condition that tests nothing about the row) stay refused. Iterator conditions in `COUNTX`/`COUNTAX` support comparisons when the local operand types can be verified: equality/inequality supports matching numeric, Boolean, or text operands, while ordering comparisons require numeric operands. Logical operands must be Boolean or numbers (a number is True unless it is zero, iteration 87), and declared text columns cannot be coerced to Boolean even if their values spell `true` or `false`. An untyped reference may be inferred as Boolean only when paired with a Boolean expression and only if the row value parses as `true` or `false`. Text equality is limited to same-table text columns or a text column and string literal, using Unicode case-folding. Mismatched, date/time, and unverifiable operand types reject. Model-specific collation is not stored. This is not a complete context-transition, lineage, or expanded-table implementation.
- `RELATED` is supported only inside those measure iterators, with one qualified numeric target column and one direct active, unambiguous many-to-one relationship from the iterated row to the lookup table. Numeric keys use typed numeric equality; text keys use Unicode case-folded equality because project metadata does not store model collation. This shared local comparer is also used by relationship filtering and one-side uniqueness checks. It approximates a common case-insensitive collation and may differ from locale-specific model behavior. Case-fold collisions on a one side are rejected during relationship validation and source refresh. The lookup scans the complete related table regardless of its applied filters; a key without a matching row returns BLANK. It does not support text results, inactive or multi-hop relationships, one-to-one or many-to-many links, calculated columns, `RELATED` inside `FILTER`, or general row-context stacks.
- Relationship paths support the current saved cardinality, direction, active/inactive, and ambiguity rules. This is not a complete Tabular relationship engine.
- Filter functions are limited to enumerated forms. A function accepted by the parser may reject other argument arrangements or combinations.
- `DIVIDE` supports two arguments or three arguments with a numeric literal (optionally prefixed by one unary sign) or exactly `BLANK()` as the alternate. A zero denominator with `BLANK()` returns the local blank marker. Direct `BLANK()` numerator and denominator operands are supported; a blank denominator follows the zero-denominator default/alternate path, while a blank numerator stays blank even with a zero or Boolean denominator and a numeric alternate. For nonblank Boolean operands, the local `DIVIDE` path converts `TRUE()` to 1 and `FALSE()` to 0, matching the tested Power BI Desktop 2.157.879.0 forms. Tested nested blank-producing `COALESCE` and `DIVIDE` operands also remain blank; the outer `COALESCE` can replace that result as usual. Power BI returns blank for `ABS(BLANK())`; the local evaluator preserves that value in the existing `COALESCE` path, for the exact `ABS(BLANK())` `DIVIDE` operand, and as a tested blank denominator. Standalone scalar-measure validation still rejects `ABS(BLANK())`. It also matches the tested `COALESCE(BLANK() + 1, 7)` result. Other blank-containing forms are not covered. Arithmetic, function, aggregate, and measure-reference alternates reject, even when constant-looking. These are tested cases, not general blank coercion or full `DIVIDE` parity. The Boolean-denominator result does not establish short-circuit evaluation; the local evaluator evaluates both operands before returning a blank numerator.
- Calculated tables, calculated columns, and measures have separate lifecycle semantics; behavior of one object kind must not be inferred from another.

## Measure authoring support

The current Home and Modeling ribbons expose **New DAX measure**, and Model view exposes the same action when a table is loaded. The native measure editor has a searchable insert list for the <!--gen:functions-->329<!--/gen--> names in `_FUNCTIONS` plus the parser's `TRUE`, `FALSE`, `BLANK`, and `DISTINCT` special forms, qualified references to fields in loaded model tables, and references to saved measures. Every recognized name inserts a local syntax template and selects its first editable argument; these templates do not imply full Microsoft signatures or behavior. `RELATED` inserts its qualified target-column template and follows only the bounded relationship form above. `MAXX` and `MINX` insert two-argument table/row-expression templates and display their supported local scope. The editor links to Microsoft's 250+ function catalog and labels the evaluator as partial. **Validate / preview** evaluates a draft against the current page/report and relationship context without saving it or changing report filter diagnostics/cache state. It does not include a visual-specific filter context. Validation and preview use the same bounded local parser and evaluator described above.

### Distinct-count forms — 2026-10-12

`DISTINCTCOUNT([Column])` and `DISTINCTCOUNTNOBLANK([Column])` accept one column reference and work as saved measures in the local evaluator. For `DISTINCTCOUNT`, the normalized blank marker counts once when at least one row is present; `DISTINCTCOUNTNOBLANK` omits it. Both return blank when the evaluated rowset contains no rows. The latter no-row result follows the local aggregate convention; Microsoft's page explicitly documents the no-row result for `DISTINCTCOUNT` but does not state it on the `DISTINCTCOUNTNOBLANK` page. The Quick Measure picker and searchable function list can insert the nonblank form. A scalar distinct-count call is also accepted in the tested `COUNTX`/`COUNTAX` iterator expression subset.

The local table normalizes null and empty text to the same cell value, so those cannot be counted separately. Text distinctness currently uses exact local strings because the project does not store model collation; case/accent behavior can differ from a Power BI model. Zero and whitespace-only strings remain ordinary values. Microsoft documents that `DISTINCTCOUNT` counts BLANK and returns BLANK for no rows, and that `DISTINCTCOUNTNOBLANK` skips BLANK: [DISTINCTCOUNT](https://learn.microsoft.com/en-us/dax/distinctcount-function-dax), [DISTINCTCOUNTNOBLANK](https://learn.microsoft.com/en-us/dax/distinctcountnoblank-function-dax). This local implementation has no differential Tabular oracle and is not a claim of full DAX parity.

`COUNTX` and `COUNTAX` accept a loaded table or supported `ALL` table expression and one row expression. In this local measure-only subset, `COUNTX` counts nonblank numeric or text results and skips Boolean results; `COUNTAX` counts nonblank numbers, text, and Booleans. Direct text columns, numeric row expressions, Boolean expressions, empty-string expression results, blanks, and simple `IF` results are covered. Iterator `IF` conditions support comparisons when operand types can be verified: equality/inequality allows matching numeric, Boolean, or text types, and ordering requires numeric operands. Text equality is limited to text-typed columns, string literals, and supported text-producing `IF` branches; supported arithmetic and scalar expressions are type-checked, while mismatched, date/time, and unverifiable operand types reject. Numeric scalar functions validate the declared categories of their inputs, and iterator row expressions are checked against the correct table schema even when a table is empty. Scalar aggregate column references resolve their type from the aggregate's own model table, independently of the current iterator row. Nested supported iterators may use their own loaded table or `ALL` table scope; references from the inner row expression to an outer table row are unsupported. String matching uses Unicode case-folding because the model does not store a DAX collation. The evaluator does not implement general DAX type coercion. Formula-produced `""` counts, while stored empty cells and `BLANK()` results are skipped after local blank normalization. When no countable result exists, including an empty table or all-blank/Boolean-only `COUNTX` input, `COUNTX`/`COUNTAX` return `BLANK()`; `COUNTX` skips Boolean results and `COUNTAX` counts them. Blank is preserved through direct measure references, the supported `CALCULATE` wrappers, draft preview, KPI/card values, grouped chart points, and matrix cells. A numeric zero remains distinct. The evaluator still coerces blank to zero in numeric operators through its current `as_number` helper; operator-specific DAX blank coercion is not implemented. General table expressions, cross-table row references, and calculated-column use remain unsupported. Microsoft documents these functions at [COUNTX](https://learn.microsoft.com/en-us/dax/countx-function-dax) and [COUNTAX](https://learn.microsoft.com/en-us/dax/countax-function-dax).

**COUNTX/COUNTAX blank inference boundary:** Microsoft's documentation says these functions return blank when there are no rows to count or aggregate and identifies `COUNTAX` for logical values. Applying that wording to a nonempty all-blank iterator and a Boolean-only `COUNTX` is an inference because the references do not show those exact examples. No external Tabular engine was used as a differential oracle. This local contract is covered by evaluator and report lifecycle tests; it is not a claim of Microsoft-engine parity.

## Table and Slicer measure behavior — 2026-10-12

Table visuals accept column and measure fields together. Assigned columns define distinct row groups, and each saved measure is evaluated under that row's filter context; multiple measures are supported. A measure-only Table evaluates one total-context row. Table row selection uses the first displayed column field as its cross-filter category, even when a measure appears first in the field list or an older saved visual omits `table_id`. If a source refresh removes an assigned dimension, the Table displays an explicit stale-field message instead of a blank category with a grand-total measure. A missing or failing saved measure also produces an evaluation message instead of appearing as a genuine blank. Slicers accept columns only: measure choices are hidden and rejected, and persisted invalid measure bindings yield no selectable values.

This is a bounded report feature, not general DAX visual-query behavior. A Table remains bound to one model table; cross-table grouping, grouped-table total rows, broader relationship-driven query context, and explicit no-data row options remain unsupported. The behavior is covered by local evaluator/report lifecycle tests, not by comparison with a Tabular engine. Microsoft documents measures as context-dependent visual values and Table visuals with category columns plus measures at [measures in Power BI](https://learn.microsoft.com/en-us/power-bi/transform-model/desktop-measures) and [Table visuals](https://learn.microsoft.com/en-us/power-bi/visuals/power-bi-visualization-tables?tabs=powerbi-desktop); slicers use field values at [Slicer visual](https://learn.microsoft.com/en-us/power-bi/visuals/power-bi-visualization-slicer-visual).

### Scalar math — 2026-10-21 (iteration 64)

`INT`, `TRUNC`, `SIGN`, `SQRT`, `EXP`, `LN`, `MOD`, and `POWER` work in measures and calculated columns. Expected values come from a differential run against the running Power BI Desktop 2.157.879.0 engine (read-only ADOMD, `tools/dax_oracle_diff.py`, 49 edge expressions): 47 match, including inputs both engines reject; the 2 remaining differences are listed below.

- `INT` floors toward negative infinity (`INT(-2.5)` is `-3`). `TRUNC(number[, digits])` truncates toward zero and accepts negative digits (`TRUNC(1234,-2)` is `1200`); fractional digits round like `ROUND`'s (`TRUNC(1234.567,1.9)` is `1234.56`), digits above 28 leave the number alone and below -28 give `0` (iteration 88). `TRUNC` and `MOD` compute with 100 digits of precision so large operands keep every digit.
- `MOD` takes the divisor's sign (`MOD(-7,3)` is `2`, `MOD(7,-3)` is `-2`). A zero or blank divisor is rejected, as Power BI raises a division-by-zero error.
- Blank handling matches Power BI, for aggregates that evaluate to blank and for a literal `BLANK()` argument: blank in, blank out for `INT`, `TRUNC`, `SIGN`, `SQRT`, `MOD`, and `POWER` (blank base); `EXP(BLANK())` is `1`; a blank `POWER` exponent counts as zero (`1`).
- Rejected where Power BI raises an error: `SQRT` of a negative number, `LN` of zero or a negative number, `POWER(0, x)` for `x <= 0`. Results larger than a double (about 1.8e308, for example `EXP(1000)`) are rejected as outside the supported numeric range, as in Power BI. Negative zero is reported as `0`.
- **Known gaps:** `LN(BLANK())` is rejected locally; Power BI returns `-Infinity`. `POWER` of a negative base with a non-integer exponent is rejected locally, but Power BI returned `-2` for `POWER(-8, 1/3)`, so its rule for that case is not modeled. Irrational results are exact `Decimal` values; Power BI returns doubles (about 15 significant digits).

### Blank arithmetic, conditionals, rounding to a multiple, more aggregates — 2026-10-21 (iteration 65)

Verified side by side against the running Power BI Desktop 2.157.879.0 engine (`tools/dax_oracle_diff.py`, read-only ADOMD): **264 distinct expressions (`tools/dax_battery_blank_logic.json` plus the earlier batteries): 230 match, 34 are refused locally and 0 differ.** Every "refused" row is a documented gap below, never a wrong value.

- **Blank arithmetic** (measures and calculated columns). `+` and `-` treat blank as zero unless both sides are blank (`BLANK()+1` is `1`, `BLANK()+BLANK()` is blank); `*` and `/` return blank when the left side is blank (`BLANK()*5`, `0*BLANK()`, `BLANK()/0`). This changes earlier behaviour, where blank*x was `0`: a calculated column `[Quantity]*[Unit price]` is now blank for a blank quantity, as in Power BI, so such rows drop out of visuals the same way. A literal `BLANK()` is now accepted inside arithmetic, comparisons, `IF`, `ISBLANK`, `IFERROR`, `SWITCH`.
- **`IF`** takes two arguments (false branch is blank). **`ISBLANK`** is true only for blank (`ISBLANK(0)` is false). **`IFERROR(value, alt)`** returns `alt` for data errors (division by zero, `SQRT` of a negative, `LN(0)`, `FLOOR(x,0)`, results beyond a double); blank stays blank and `DIVIDE(1,0)` is blank, not an error. Unsupported syntax is never swallowed.
- **`SWITCH(expr, value, result, …[, else])`** compares strictly and stops at the first match: blank matches only blank (`SWITCH(BLANK(),0,…)` falls through), and comparing a number with `TRUE()`/`FALSE()` is an error. `SWITCH(TRUE(), cond, result, …)` works.
- **`CEILING`/`FLOOR(number, significance)`**: exact `Decimal` results; `CEILING(x,0)` is `0` but `FLOOR(x,0)` is an error; a positive number with a negative significance is an error; two negatives round the magnitude (`CEILING(-2.1,-1)` is `-3`, `FLOOR(-2.1,-1)` is `-2`); blank number gives blank, blank significance counts as zero.
- **`MEDIAN`, `PRODUCT`, `COUNTBLANK`** over one column. `COUNTBLANK` returns blank (not `0`) when nothing is blank, as Power BI does; `PRODUCT` beyond double range is an error.
- **Known gaps (refused locally):** `x/0`, `x/BLANK()` and `0/0` are Infinity or NaN in Power BI. A formula where such a value reaches a comparison, `ISBLANK` or `SWITCH` is refused rather than guessed (`IFERROR(1/0>1, 2)` is `True` in Power BI), and a bare `1/0` is refused. Not yet supported: boolean or text results (`AND(TRUE(),FALSE())`, `SWITCH` returning text, `"a"="A"`), `VAR/RETURN`, the `^` operator, `ABS(BLANK())`, text functions, `VALUES`/`SELECTEDVALUE`/`HASONEVALUE`, `TODAY`, `FORMAT`, `MAXX(FILTER(...))`, `ISBLANK` over a text column aggregate, and the two scalar-math gaps from iteration 64. The new functions also work inside row iterators (`SUMX(Facts, IFERROR(Facts[Sales]/Facts[Quantity], 0))`, `SWITCH`, `CEILING`, `FLOOR`, two-argument `IF`): all 15 iterator expressions now match Power BI (the one `MAXX` refusal was fixed in iteration 66).

### Review fixes and the load rules for text — 2026-10-21 (iteration 66)

Verified live against Power BI Desktop 2.157.879.0 with a real workbook (`Downloads/DSI.xlsx`, Tally purchase-invoice list, 371 data rows × 10 columns) loaded **by Power BI's own Power Query engine** into a scratch table (`tools/table_oracle_diff.py`: TMSL `createOrReplace` with an M partition on the unsaved model, no UI), every cell dumped through ADOMD and compared with the local importer and the local evaluator. **Cells: 371 × 10 identical. Measures: 108 expressions over the table, 106 match, 2 refused, 0 differ.** Merged DAX batteries: 289 expressions, 251 match, 38 refused, 0 differ (the 15 iterator expressions all match now).

- **Text in the loaded model (new, found by the workbook comparison).** Power BI's model is not the Power Query result: it drops trailing characters U+0000–U+0020 (space, tab, LF, CR, VT, FF, control characters) from every loaded text value, keeps leading spaces and non-breaking/ideographic spaces, turns a whitespace-only value into empty text, treats ASCII letters case-insensitively (`DISTINCTCOUNT`, grouping, `Column = "text"` filters) and stores every spelling under the **first one seen**. Non-ASCII letters stay distinct (`é`/`É`, `σ`/`Σ`, `ß`/`ss`). Calculated tables keep trailing spaces (the rule belongs to loading, not to the engine). `DSI.xlsx` has `PREPAID CARDS ` (trailing space) in a Party Name column: Power BI stores `PREPAID CARDS`, a filter on `"PREPAID CARDS "` matches nothing, and `DISTINCTCOUNT(Remarks)` is 160 not 163. The model candidate (`_model_candidate_with_format_errors_as_blank`) now applies these rules; the Power Query candidate and the Power Query preview keep the raw values. The previous local behaviour (case-sensitive filters, Unicode `casefold` for `COUNTX` conditions) is replaced by the observed rule for column filters and `DISTINCTCOUNT`.
- **Excel numbers.** Excel writes doubles with 17 digits (`66.150000000000006`); Power Query reads the double, so the importer now keeps the shortest round-trip text (`66.15`). Sums no longer differ at the 13th decimal.
- **Review fixes (independent critic, six defects):** `0*-1` and `PRODUCT` no longer show `-0`; `+ - * /` raise the double-range error instead of returning `1E+309` (and `IFERROR(1E308+1E308,3)` is `3`); `CEILING`/`FLOOR` of huge numbers keep every digit; `MAXX`/`MINX`/`COUNTX`/`COUNTAX` accept `IF` (two or three arguments), `IFERROR`, `ISBLANK` and `SWITCH`; division by zero used directly as a condition (`IF(1/0,…)`, `AND`, `OR`, `NOT`) is now refused instead of being swallowed by `IFERROR` (Power BI treats the Infinity as TRUE). `ABS(BLANK())` and `CALCULATE(BLANK())` stay blank inside `IF`/`COALESCE` as in Power BI; `ROUND(BLANK(),0)` inside `IF` is refused (Power BI returns blank, the local answer was `0`).
- **Known gaps found this iteration:** `COUNTROWS(FILTER(T, …))`, `SUMX(FILTER(T, …), …)` and the other iterators over a `FILTER` table are refused (the two non-matching rows of the workbook battery); the load rules are applied only where the app loads a query into the model, not to the results of calculated columns or DAX tables; string collation outside ASCII for scalar text comparison (`"é"="É"` is `True` in Power BI) is not modelled. `ROUND(BLANK(),0)`, `MAXX` over Boolean results and `Infinity`/`NaN` stay refused.
- **Iteration 67 — `FILTER` as a table argument:** `COUNTROWS`, `SUMX`, `AVERAGEX`, `MAXX`, `MINX`, `COUNTX` and `COUNTAX` accept `FILTER(table, predicate)` or `FILTER(ALL(table), predicate)`. The predicate language is the `CALCULATE` `FILTER` subset (a column compared with one scalar literal, joined with `&&`, `||`, `AND`, `OR`, `NOT`; blank numbers equal 0 and blank text equals `""`, ASCII-insensitive text). 33 live expressions and the DSI.xlsx 108-expression battery match Power BI (`tools/dax_battery_filter_tables.json`). `FILTER(ALL(…), …)` remains unsupported as a `CALCULATE` filter argument; predicates comparing two columns remain refused.

### Iteration 88 — nested row contexts, strict `==`, text as True/False, small functions (Power BI Desktop 2.157.879.0)

Verified live (about 47,000 fresh probes plus hand-built matrices on the Facts scratch table, the ZO / ZB / ZS relationship models and a text / Boolean scratch table; 0 differences on the frozen sets, `tests/fixtures_iter88_fresh.json`).

- **CALCULATE / CALCULATETABLE inside the scalar side of a True/False filter** now works in any row context (inside `SUMX`, under an outer `CALCULATE`): the filter is `FILTER(ALL(columns), test)` where the columns include those read by the tests of the CALCULATETABLE; `KEEPFILTERS(test)` reads like the plain test. Several scalars in one filter, mixed readings and nested CALCULATETABLE inside a row context are refused.
- **Nested iterators read the columns of enclosing row contexts** (`SUMX(Facts, SUMX(ROW("a",1), Facts[Quantity]))` is 15); `EARLIER(col, n)` is positional (the n innermost row contexts are skipped) and `EARLIEST` reads the outermost; a renamed `SELECTCOLUMNS` column is not addressable as `T[col]`. The body of an iteration without rows is still validated (a column no nested iteration and no enclosing row context holds is an error). The walk order of `CONCATENATEX` / `TOPN` ties over an expression that depends on an enclosing row context (or `OFFSET`, or a `CALCULATETABLE` over a table) is not modelled: refused unless the ORDER BY is total. A BLANK ranks below 0 in `TOPN`.
- **Text and comparisons.** A `/* */`, `//` or `--` comment may stand between a table name and its `[column]`. `a == b` is strict (BLANK is not 0 and not ""; a type mismatch is an error; non-ASCII text is refused). Text as a condition: "" is FALSE, TRUE / FALSE in any case, a number spelled in text is TRUE unless it is zero, anything else is an error. Text comparison with full-width or half-width forms is refused (Power BI ignores the width).
- **Functions.** `AVERAGEA` / `MAXA` / `MINA` of a text column count every text as 0 and True / False as 1 / 0; `STDEV.S` / `VAR.S` of fewer than two values is NaN (BLANK of none); `PERCENTILE.INC(col, BLANK())` is the minimum (EXC of BLANK is an error); `ISO.CEILING` ignores the sign of the significance and a BLANK one is 0; `HOUR` / `MINUTE` / `SECOND` of time-only text (`"13:45"`, `"1:45 PM"`, `"13:45:30"`).
- **Still refused (documented gaps):** `DIVIDE` with a text or Boolean alternate result, `LN(BLANK())` (Power BI: -Infinity), table-valued results at the top of a measure (`ROW`, `DATATABLE`, `TOCSV`, `TOJSON`), `SUBSTITUTEWITHINDEX`, `INFO.*`, `EVALUATEANDLOG`, `VAR` blocks in a filter or after an operator.
